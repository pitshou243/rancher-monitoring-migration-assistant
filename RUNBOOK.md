# Monitoring migration review and execution runbook

This runbook is a review checklist accompanying the read-only assistant. It is not a universally tested procedure. Choose exact source/target versions with Dev/QA and verify subscription support separately.

## Before changes

1. Confirm you are targeting the affected downstream cluster. Capture runtime and CRD release names using Helm; singular/plural CRD release naming can vary. Do not infer a name.
2. Run `assess`, then `export`. Resolve collection failures; back up inline and referenced configuration. Save existing runtime values, templates and credentials.
3. Back up persistent data separately: Prometheus TSDB, Grafana database/configuration and Alertmanager state if needed. Record PV/PVC names, reclaim policy, ownership and volume locality. Test recovery.
4. Review custom resources that are Helm-owned. Runtime uninstall can remove them even when CRDs remain. Separately export supporting ConfigMaps and dependencies.
5. Generate `prepare` outputs, then inspect exact target chart values and templates using Helm with a pinned version. Verify candidate keys, CRD hooks, image pull requirements and target service names. Do not reuse legacy values wholesale.
6. Rehearse in nonproduction. Define an interruption window, notification continuity plan, and rollback criteria. Preserve control-plane collection and any HPA/Project Monitoring dependencies.

## Reviewed transition

1. Uninstall only the legacy runtime after backups and recovery validation. Preserve the monitoring CRD release at this stage. Avoid the generic UI uninstall path that removes both.
2. For the preserved-CRD approach supplied by Dev, review `crds.upgradeJob.enabled: true` with `--skip-crds` against the exact target runtime chart. Review permissions, hook images and changed CRD schemas. Hook failure requires investigation before proceeding.
3. Install the replacement runtime under a name other than `rancher-monitoring` in `cattle-monitoring-system`. Set intended CR and namespace selectors, existing Alertmanager config Secret, Grafana credentials, persistence and runtime sizing. Restore lost independent/custom resources only after inspecting their exported manifests.
4. If restoring volume contents, scale the relevant workload down and ensure there is no writer before restoring. Storage cloning via `dataSourceRef` depends on the CSI driver, Kubernetes features and CRD schema; it is not generated by this tool. Never share one writable Prometheus TSDB between instances.
5. Install the dashboard chart. Configure proxy services using actual rendered runtime names/ports and review Grafana embedding/authentication settings. Configure distribution-specific collection, including the reviewed Prometheus Agent alternative where appropriate.
6. Run `validate` with the same baseline and context; include the optional Prometheus URL if captured originally. Check custom metrics and controlled notifications manually.
7. Only after confirming the new stack manages compatible CRDs and reviewing the old CRD release's manifest/hooks, perform Dev's proposed old CRD-release cleanup using Helm `uninstall --no-hooks` and the actual release name. Do not uninstall that release through the UI. `--no-hooks` suppresses hooks; it does not prevent deletion of ordinary resources in a release manifest. Confirm where the installed version keeps CRDs before using this step.

## Rollback

Do not assume reinstalling the old chart reverses a CRD schema upgrade. Test old operator compatibility with resulting CRDs in the rehearsal environment. Keep original chart/version, values, resources and recoverable data copies.

If rollback is required, stop new data writers, assess whether CRDs must be restored under Dev guidance, restore the prior runtime/configuration and its data through the tested procedure, then validate scraping and notification delivery. Define how samples collected after cutover are handled. No automatic rollback is implemented.
